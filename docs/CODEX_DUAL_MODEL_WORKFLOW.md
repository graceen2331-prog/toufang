# Codex 双模型工作流：Luna 执行 + Sol 推理

## 1. 角色分工

- **GPT-5.6 Luna（默认主执行）**：读取代码库、检索资料、运行命令、修改代码、补测试、执行验证、检查 diff 和完成交付。
- **GPT-5.6 Sol（按需只读顾问）**：处理复杂架构设计、跨模块决策、疑难 Bug 和高风险方案评审。Sol 不直接修改工作区。

新任务默认由 `.codex/config.toml` 选择 `gpt-5.6-luna`。如果用户或任务界面显式选择了其他模型，显式选择会覆盖项目默认值。

## 2. 路由规则

Luna 先完成必要的轻量探索，并判断任务是否满足升级条件。不满足时由 Luna 独立完成，不调用 Sol。

满足以下任一条件时，先暂停实现并升级给 Sol：

1. 设计会同时影响三个及以上模块，或涉及数据库 schema、状态机、审批门、权限边界、公开 API 合约。
2. 存在两个以上都合理的架构方案，需要在一致性、复杂度、性能、兼容性或迁移成本之间做取舍。
3. Bug 涉及并发、事务、队列、缓存、事件顺序、跨租户隔离，或 Luna 已进行两轮有证据的定位/修复仍未解决。
4. 变更涉及认证、资金、数据删除或丢失风险、生产迁移、对外发送等高风险领域。
5. 需要对关键假设进行深度反证，错误决策会造成大范围返工。

以下任务通常不升级：代码搜索、文件读取、依赖定位、常规命令、局部且根因明确的修复、格式调整、普通 CRUD、补单测、执行既定方案和验证结果。

## 3. Task Packet 规范

调用 Sol 时，Luna 必须新建一个不继承完整会话的子代理，只发送 Task Packet。目标长度为 **1,000～3,000 Token**，不得粘贴完整项目上下文、长日志或无关文件。

Task Packet 使用以下结构：

```markdown
# Task Packet

## 当前目标
一句话说明要做出的决策或要解决的问题，以及成功标准。

## 已知事实与现状
- 当前行为、可复现证据、错误信息或关键数据。
- 只保留影响判断的事实，标明哪些是推断。

## 关键代码
- `path/to/file.ts`：相关符号及职责。
- 仅附必要的 5～30 行代码片段；全部代码片段尽量控制在 800 Token 内。

## 核心约束
- 架构、兼容性、安全、数据一致性、审批边界和验收要求。

## 已尝试方案
- 尝试内容、结果和为什么仍未解决；未尝试则写“无”。

## 待解决问题
1. 需要 Sol 明确回答的决策问题。
2. 需要 Sol 检查的失败模式或反例。

## 期望输出
结论与根因、推荐方案、变更矩阵、风险与取舍、验证计划、待确认项。
```

压缩规则：

- 用文件路径、符号名和行为摘要代替整文件。
- 日志只保留首个根因、关键堆栈和能够排除假设的行。
- 不重复 `AGENTS.md`、Playbook 或已知项目背景，只摘录会改变本次判断的约束。
- 不发送密钥、令牌、个人数据或生产敏感信息。
- 如果 Packet 超过 3,000 Token，先删除历史叙述、重复证据和非关键代码。

## 4. Sol 输出契约

Sol 必须返回：

1. 结论与根因，并区分事实、推断和未知项。
2. 一条优先推荐的结构化方案。
3. 按文件或模块划分的变更矩阵。
4. 主要风险、取舍、失败模式和必要的回滚点。
5. 单测、集成测试、E2E 与人工验收计划。
6. 只包含会改变方案的待确认项。

Sol 不运行命令、不修改代码、不扫描完整仓库。信息不足时，只要求最小补充证据。

## 5. 返回 Luna 执行

Luna 收到方案后负责：

1. 对照实际代码验证 Sol 的关键假设，不能把顾问结论当成已验证事实。
2. 将方案转成项目内的具体改动，遵守 `docs/CODEX_PLAYBOOK.md`。
3. 修改代码、补测试、运行 `pnpm check` 和相关 E2E。
4. 如果验证结果推翻方案，先基于新证据自行调整；只有出现新的关键决策时才再次调用 Sol。
5. 汇报最终实现、验证结果、剩余风险，以及 Sol 方案中未采纳的部分和原因。

同一个决策周期默认只调用 Sol 一次，避免重复推理和上下文浪费。
