# 生产上线计划

> 状态日期：2026-09-05。本文是上线工作的统一入口；功能分波验收仍以 `docs/CODEX_PLAYBOOK.md` 和各波提示词为准。

## 当前结论

W0–W11 的产品功能和自动化验收已经完成，项目处于“代码上线准备”阶段，不等于已经满足生产发布条件。

当前可复现的代码质量基线：

- `pnpm check`：TypeScript、ESLint、单元测试；
- `pnpm build`：Next.js 生产构建；
- `pnpm test:integration`：隔离 PostgreSQL/Redis、真实迁移、数据库集成测试；
- `pnpm e2e`：隔离 PostgreSQL/Redis、fake AI、完整浏览器验收；
- GitHub Actions 同时执行上述四道门禁；
- Playwright 自动拦截未处理的 `pageerror` 和 React hydration 错误。

## 上线范围与门禁

### P0-A：代码质量门禁

- [x] 修复共享权限门的 SSR/客户端 hydration 不一致。
- [x] E2E 对浏览器未处理异常和 hydration 错误自动失败。
- [x] CI 固定 Node.js 与 pnpm 版本，执行 check、build、integration、e2e。
- [ ] CI 在真实 GitHub 仓库首次运行并全部通过。
- [ ] 合并前确认变更只包含计划内文件，且保护分支要求两个 CI job 通过。

### P0-B：部署拓扑门禁

以下事项必须先由部署环境负责人确定，不能用开发机 `docker-compose.yml` 直接替代：

- [x] Web 提供无需登录的 `/api/health/live` 与 `/api/health/ready`，供部署平台执行存活和就绪探测。
- [ ] Next.js Web 与 BullMQ Worker 作为两个可独立启动、重启和扩容的长期进程。
- [ ] 使用受限网络内的生产 PostgreSQL（含 pgvector）与 Redis；明确连接上限、Redis 淘汰策略和持久化策略。
- [ ] 明确文件存储方案。知识文档等不可再生业务文件必须使用对象存储或有备份的持久共享卷，不能依赖临时容器文件系统。
- [ ] 反向代理保留 Origin / Fetch Metadata 请求头，覆盖可信单值客户端 IP 头，并禁止绕过代理直连应用端口。
- [ ] 生产密钥由密钥管理服务注入，三类安全密钥分别生成且不得复用；生产环境禁用演示登录。
- [ ] 在 staging 使用与生产一致的进程拓扑完成一次启动、重启和滚动发布演练。

部署平台确定后，另行实现并评审对应 Dockerfile、镜像发布或平台配置；当前不预设 Vercel、Kubernetes 或单机方案。

### P0-C：数据迁移、备份与回滚门禁

- [ ] 发布前创建数据库备份，并记录备份标识、保留期和负责人。
- [ ] 迁移只由一个发布步骤执行 `pnpm exec prisma migrate deploy`，Web/Worker 实例不得并发执行迁移。
- [ ] 在 staging 从备份恢复一次，并验证登录、Campaign、审批、付款、知识文档与审计数据。
- [ ] 数据库变更遵循 expand/contract；应用回滚只回退应用版本，不默认执行破坏性数据库降级。
- [ ] 明确发布失败的停止条件、回滚负责人、上一稳定版本和预计恢复时间。

### P0-D：真实 AI 验收门禁

自动测试继续使用 fake provider，普通 PR 不读取真实密钥、不产生付费调用。首发启用的 AI 路径必须在 staging 使用一个生产候选 Provider 完成：

- [ ] Admin → AI 设置的连接测试通过，密钥加密保存且日志不泄露原文。
- [ ] 策略生成、达人发现/评分、Brief、外联起草、内容审核/报告、知识问答分别完成至少一次真实模型闭环。
- [ ] 验证结构化输出解析、超时、重试、限流、人工审批暂停和失败提示；不得只验证单次聊天响应。
- [ ] 使用固定的小型验收样本记录输入版本、模型、结果、耗时、token 与成本，形成可复查证据。
- [ ] 设置单次运行和组织月度成本阈值；确认超限时拒绝新调用且不影响人工业务流程。

如果首发产品不能关闭 AI 功能，以上全部是整站上线硬阻塞；若后续提供经过验收的 AI feature flag，则可改为“启用 AI 前硬阻塞”。

### P0-E：可观测性与值守门禁

现有 Agent 运行监测只覆盖应用内模型调用，不能替代基础设施监控。上线前至少需要：

- [ ] Web 可用性、P95 延迟、5xx 比例与未处理异常告警。
- [ ] Worker 心跳、队列深度、最老等待任务、失败任务和重试耗尽告警。
- [ ] PostgreSQL 连接数/容量/备份状态，以及 Redis 内存/连接/淘汰与持久化状态告警。
- [ ] 文件存储容量、写入失败和备份状态告警。
- [ ] 为每条告警定义接收人、响应时限和处置手册，并完成一次测试告警。

监控产品随部署平台选择；Langfuse 只能作为 AI 追踪补充，不能代替上述基础告警。

## 可带风险上线与 P1

在有限用户、明确容量上限且有人值守的首发中，可记录风险后延期：

- 第二个及更多 AI Provider 的完整兼容矩阵；
- 大规模压测、自动扩缩容和多区域容灾；
- 更大的 AI 质量评估集与长期成本优化。

默认列为 P1：

- README 已声明 Deferred 的内容平台发布、指标回传、电子签和支付连接；
- Langfuse 接入及高级 Prompt/Trace 分析；
- 生产级文档解析、知识权限分层和增量重嵌入；
- 全自动回滚和跨区域故障转移。

P1 项只有在销售合同、客户承诺或首发流程明确依赖时，才升级为 P0。

## 发布执行顺序

1. 冻结发布候选提交，CI 的“静态检查与构建”“集成与端到端测试”全部通过。
2. 在 staging 部署同一提交，执行数据库备份与 `prisma migrate deploy`。
3. 启动 Web 和 Worker，验证健康状态、队列消费、文件读写与测试告警。
4. 运行 fake provider 的完整浏览器验收，再执行真实 AI 小样本 smoke。
5. 产品、研发、运维分别确认业务范围、变更清单、已知风险和回滚点。
6. 生产发布先迁移、后 Web、再 Worker；观察核心指标后逐步放量。
7. 发生数据完整性风险、持续 5xx、Worker 不消费、登录异常或 AI 大面积失败时停止放量并按预案回滚。

## 本轮不做

- 不在普通 CI 或 PR 中调用真实付费模型。
- 不把真实密钥写入仓库、Actions 变量或测试日志。
- 不在部署平台未知时提前固化 Dockerfile、镜像或 Serverless 配置。
- 不把第三方平台集成或 Langfuse 插入当前 P0 代码路径。
- 不用 `suppressHydrationWarning` 或宽泛忽略 `console.error` 掩盖运行时问题。
